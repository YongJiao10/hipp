# Formal gradient-spectral refresh and Lynch20 correction

Date: 2026-07-13

## Objective

Every active formal `gradient-spectral` result must be generated by the fixed
shifted-cosine implementation and have machine-checkable provenance. Stanford
HC/Symp, HCP weighted-fisherz, and Lynch2024 results must be refreshed. The
Lynch taxonomy must be corrected from the misleading `21net` name to the actual
20 non-Noise networks.

## Formal scope

The maintained active result set is:

1. HCP Kong2022 RouteA canonical8 and family17, Fisher-z and count. The current
   shifted-cosine group results are retained; their overviews are re-rendered
   only as needed for the strengthened presentation provenance contract.
2. HCP Kong2022 RouteA weighted-fisherz, derived from the new RouteA group
   result. Existing WTA products remain method-isolated and are not treated as
   gradient-spectral provenance.
3. Stanford Kong2022 HC and Symp subgroup results, each with Fisher-z and
   weighted-fisherz gradient-spectral products.
4. HCP Lynch2024 20-net and canonical8 results, using shifted-cosine and final
   K=3 after K=2..8 diagnostics.

RouteB, ctxreg, ctxdrop, and other experimental gradient-spectral branches stay
archived and are not recomputed. Continuous HippoMaps gradient products are not
affected by the affinity change, except that the Lynch gradient-bank route is
renamed from `lynch2024_21net` to `lynch2024_20net`.

## Lynch20 breaking correction

The current workflow excludes the `Noise` label before building the Lynch
reference bank, so the functional taxonomy has 20 networks even though the
route, atlas, taxonomy, paths, functions, and documentation say `21net` or
`lynch21`. The correction is deliberately breaking:

- canonical route and atlas slug: `lynch2024_20net`;
- canonical taxonomy name: `lynch20`;
- canonical group root prefix: `lynch2024_20net_nsi043_`;
- no `21net` runtime choice, alias, symlink, or compatibility fallback;
- the canonical8 Lynch route reuses the `lynch2024_20net` gradient bank;
- reference and FC materialization fail unless `Noise` is absent and the
  ordered non-Noise network count is exactly 20;
- gradient/group manifests record the 20-column input evidence and explicit
  Noise exclusion.

Correctly computed but misleadingly named `21net` inputs and results are not
silently reused as formal provenance. New `20net` references, FC caches,
gradient bank, group results, and presentation artifacts are generated under
canonical paths. The old active `21net` paths are moved to a dedicated archive
only after the new chain validates. The exact move inventory must be shown to
the user and explicitly confirmed before execution.

## Provenance contract

For every formal group combination, `group_atlas_manifest.json` must record:

- `status: ok`;
- `surface_affinity: shifted-cosine`;
- the fixed shifted-cosine description and clustering algorithm;
- requested K range `[2, 8]` and final K `3`;
- a one-component affinity graph;
- the expected dataset, route, atlas, smoothing, hemisphere, and upstream
  gradient/reference roots.

Weighted-fisherz branch manifests must retain the upstream shifted-cosine
provenance rather than presenting weighted assignment as a different clustering
algorithm.

For every formal overview, its presentation manifest must record the upstream
group manifest paths, affinity name, and affinity description. The visible
figure title or subtitle includes `shifted-cosine`; canonical PNG filenames stay
stable so downstream references do not break.

A release audit treats a PNG as formal only through its presentation-manifest
lineage. It fails on missing sources, legacy/unknown affinity, mismatched
dataset/route/atlas, incomplete combinations, or references to archived paths.
Mixed WTA/gradient README or manifest files are valid only when each item has
method-specific lineage; WTA entries are not required to carry a surface
affinity.

## Execution design

Code and documentation changes are implemented and tested before production
execution. Production runs use the explicit py314 interpreter, fixed `jobs=1`,
one sequential background worker, a safe run ID, status/PID/stdout/stderr files,
and stop-on-first-failure semantics.

The sequence is:

1. Generate and validate Lynch20 reference, FC, and gradient-bank inputs.
2. Generate Lynch20 and Lynch canonical8 gradient-spectral group results and
   overviews.
3. Refresh HCP RouteA weighted-fisherz gradient results and overview lineage.
4. Generate Stanford HC and Symp Fisher-z group results.
5. Generate their weighted-fisherz branches and overviews.
6. Re-render the already valid HCP RouteA canonical8/family17 overviews with the
   strengthened presentation provenance.
7. Run the global formal-output audit.
8. After all new products pass, present the exact old Lynch21 active-path
   archive inventory for user confirmation; archive only after approval.

No high-frequency polling is used. A root handoff records the run ID, stage
status, validation command, and any remaining confirmed archive action.

## Failure and resumption

Each stage validates its inputs before writing and its manifests after writing.
An interrupted worker leaves a failed/running status and does not advance to a
dependent stage. Rerunning with a fresh run ID may reuse only combinations whose
manifests already satisfy the full shifted-cosine provenance contract. The
global audit must remain red until every maintained combination and overview is
complete.

## Verification

Tests cover:

- removal of all `lynch2024_21net` and `lynch21` runtime choices;
- exact 20-network order with `Noise` excluded;
- Lynch8 reuse of the Lynch20 gradient route;
- shifted-cosine group and weighted-branch provenance propagation;
- overview affinity lineage and visible shifted-cosine labeling;
- Stanford HC/Symp and Lynch20/Lynch8 stage planning;
- rejection of parallel jobs and unsafe run IDs;
- global audit rejection of legacy, unknown, missing, or cross-branch lineage;
- preservation of non-gradient methods and continuous-gradient products.

The focused suite, full repository suite, compilation checks, documentation
contracts, and `git diff --check` must pass before launch.

## Non-goals

- Recomputing RouteB, ctxreg, ctxdrop, or other archived experimental branches.
- Changing K=3, the K=2..8 diagnostic policy, or the shifted-cosine algorithm.
- Recomputing HCP continuous gradients unrelated to the Lynch route rename.
- Deleting archive content or old active paths without a separately confirmed
  exact inventory.
